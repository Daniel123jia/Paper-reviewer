# 已知限制

以下是当前仓库代码的实际限制，不表示已经实现相应解决方案。

## 论文解析和证据

- PyMuPDF block 抽取不能保证双栏 PDF 的语义阅读顺序。
- 公式、表格数据、标题、图注和说明文字可能被拆成不同块。
- 无 TOC 时的章节识别是有限正则，可能错过标题或产生错序。
- 扫描页仅标记需要 OCR，系统不自动 OCR。
- Evidence ID 中含随机 snapshot UUID 前缀，重新解析不保证相同 ID。
- Evidence ID 只证明原文位置存在，不证明证据支持问题，也不是技术事实验证。

## 候选问题发现

- 没有完整的全文理解、贡献重建或论证图阶段。
- 首轮最多使用 30 块，且每页候选池最多 5 块；诊断论文实际为 25/99 块。
- 选块关键词和长度启发式可以遗漏短表格行、配置细节和跨章节联系。
- 首轮 Prompt 和代码都把候选限制为 `0–3`。
- 没有独立的创新性、方法、实验、消融、图表、公式、参考文献和全文一致性审查阶段。
- 报告中的问题数量不能作为审稿质量指标。

## 反证和技术核验

- `propose`、`challenge` 和 `deep_challenge` 使用同一环境配置模型。“独立”是角色/阶段分离，不是独立实验或独立事实来源。
- Deep Challenge 仅在启发式扩展检索的原文上运行模型，不能自动证明数学、算法、实验或引用事实。
- SymPy 核验检查的是用户输入的受限标量表达式，不能证明 PDF 公式已被正确转录。
- BLEU 核验和矩阵维度核验是针对特定文本格式的保守解析器，不是通用实验或算法验证器。
- 工具核验不会自动生成新候选问题，也没有统一的技术验证状态体系。

## 状态和报告

- `source_located`、第一轮 `supported` 和 `supported_clarification` 不应被解读为已完成技术事实验证。
- Major/Minor、证据充分度、技术验证和处置状态尚未建模为独立维度。
- 正式中文意见的准入条件为 Deep Challenge verdict 恰好等于 `supported_clarification`，这不是通用问题准入策略。
- 中文报告是固定模板拼接，没有一次全文综合生成。
- 英文报告是对中文草稿的模型翻译，程序主要校验 Evidence ID 是否完整保留。
- 论文对话与审稿 finding 是分离的数据流，对话分析不会自动进入正式审稿。

## 可审计性和质量验收

- 不保存首轮审稿的完整 Prompt、所选 Evidence ID 快照和原始模型响应。
- 数据库保存的 `model` 是请求名，没有单独保存中转站实际返回的模型标识。
- 调用没有显式设置或记录 temperature、seed 和输出 Token 上限。
- 价格依赖手工配置的每百万 Token 单价；未配置时费用为未知。
- pytest、构建和 Playwright 只能证明程序行为，当前没有专家标注的审稿质量参考集、准确率、参考集召回率或误报率验收。

## 运行和部署

- 当前是本地工作台，未配置生产 TLS、反向代理、登录限速、备份和多用户权限。
- SQLite 适合当前单机使用，没有分布式任务队列或多实例协调。
- DOCX/PDF 导出依赖本机 Pandoc、Node.js 和 Playwright Chromium。
- 真实 AI 功能依赖用户自行配置的 OpenAI 兼容端点；仓库不包含密钥。
