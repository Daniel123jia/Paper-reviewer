# P2-B professional review engine

P2-B starts from the accepted P2-A squash commit `0daf4d5b20196b50ca5a050febdbd1b07e3758a4`. It is an independent candidate-generation stage. Its output does not enter the legacy review findings or drafts and never marks a concern verified.

## Snapshot and execution contract

`POST /api/understanding-runs/{run_id}/professional-review-runs` requires an authenticated session, a configured model key, and a fully completed P2-A run. It validates the stored ReviewPlan, PaperProfile, ClaimEvidenceMap and the **frozen** `source_bundle_json`. The document ID, Source Bundle ID, PDF snapshot, SHA-256 when present, understanding run ID, and every P2-A source reference must agree. P2-A schema 1.0 and 1.1 are accepted through their existing Pydantic contracts. `limited` P2-A results may proceed, with their source limitations carried into each dimension. A new PDF parse is never substituted for this snapshot.

The optional request body is `{"review_requirements": "..."}`. It is stored on the P2-B run and exposed by the run detail API. A missing body or `null` uses the default six-dimension rules. P2-A `special_requirements` are execution constraints for P2-A only and are never copied into P2-B. The P2-B model input uses the distinct `review_requirements` field; `target_journal` remains shared paper context. Existing P2-B rows migrate with `review_requirements = NULL`.

The separate SQLite `professional_review_runs`, `professional_review_dimensions`, and `professional_review_model_calls` tables retain run state, each completed or failed dimension, and safe call metadata. `GET /api/professional-review-runs/{run_id}` returns these records, candidates and usage. A process restart marks an interrupted run `partial_failed` when any dimension was already saved, otherwise `failed`.

`backend/p2b_schema.py` defines version `1.0` of `DimensionReview`, `IssueCandidate`, and `ProfessionalReviewResult`. Every dimension is bound to document, Source Bundle, understanding run and P2-B run IDs, Prompt version and actual returned model. Candidate IDs are generated by the server; candidate status is only `unverified`. Major/minor candidate impact is not a final grade. Every candidate needs a source object supporting its observed fact, a scientific consequence and at least one verification question. Model-supplied Claim IDs, source IDs and possible counterevidence are checked against the frozen bundle and the dimension's supplied context.

## ContextAssembler and scope

`backend/p2b_context.py` scores reading units from dimension-relevant P2-A facts, claims, support relations and section terms; selects original text in reading order; expands immediate neighbors; and includes table, formula and figure text plus their **unverified** status when anchored. The context names original Evidence IDs, pages and sections. It lists every omitted reading unit ID and source limitation. Under a context cap, dimension-specific fact anchors outrank broad claim references. Source IDs in model output must be in the actual supplied pack. A partial pack remains `partial`; it cannot justify a whole-paper absence claim. A blocked source produces a limited dimension without calling the model.

The model input projects P2-A facts and claim relations to the dimension's selected source IDs. It includes a compact inventory of other claim IDs so the node can distinguish unseen evidence from a missing paper element. This avoids transmitting the full PaperProfile and ClaimEvidenceMap six times while retaining the original selected text, its neighbors, source limits and omissions. The context cap is visible in each result; it does not imply full-paper coverage.

Six `DimensionReview` records are returned when all dimensions complete or are deliberately skipped. An inapplicable dimension is skipped with a reason. Empty candidate lists require an inspection explanation. A Schema/content validation failure may use the existing bounded repair behavior without discarding other dimensions. Exhausted calls, input tokens, output tokens or duration produce `budget_exceeded`, retaining earlier dimensions. A supplier call with unknown Usage stops the run immediately and remains unknown rather than being counted as zero. Deployment limits use `P2B_MAX_CALLS`, `P2B_MAX_INPUT_TOKENS`, `P2B_MAX_OUTPUT_TOKENS`, and `P2B_MAX_DURATION_MS` (defaults 18, 180000, 50000, 1800000). Call rows store dimension, Prompt version, Source Bundle ID, supplied source IDs, requested and returned model, Tokens when known, duration, status and an error class. No raw model input, response or key is written to these tables.

The first Shaw 2018 P2-B run recorded 161,174 known input tokens for D1-D5; D6 ended with unknown Usage and no later request. Reconstructing the corrected six dimension inputs indicates roughly 194k supplier input tokens for a normal six-call pass, while the local character estimator undercounted the five known calls by about 1.83x. For a separately authorized rerun, the planning recommendation is `P2B_MAX_CALLS=8`, `P2B_MAX_INPUT_TOKENS=240000`, `P2B_MAX_OUTPUT_TOKENS=50000`, and `P2B_MAX_DURATION_MS=1800000`. These are local stop limits, not supplier account hard limits or a fee guarantee; unknown Usage may still be billable.

For run `53cefd6dc9cd423fbba37ff22b9c53f0`, the D6 audit row records `unknown_usage:APIConnectionError`, 97,273 ms, null input/output Token fields, and no returned model identifier. It is the sixth and final supplier attempt. The saved material has no provider request ID or lower-level transport event proving whether the failure occurred before response streaming or during a stream, so that cause remains unknown and no zero-cost assumption is made. The frozen P2-A ReviewPlan also contains a natural-language exclusion of review findings from its N1-N3 scope; current P2-B applicability did not treat that text as an exact D1-D6 exclusion, and this fix does not rewrite the historical plan.

## Professional rules

Six versioned prompts under `backend/prompts/p2b/` implement D1 innovation, D2 theory and method, D3 experiment and results, D4 argument consistency, D5 reproducibility and D6 literature positioning. Every system prompt also includes `shared-rules/v1` and either `ai-algorithm/v1` or `generic-academic/v1`. The latter records `domain_specific_rules_unavailable`; it is not a claim of complete specialist coverage. ReviewPlan can exclude a dimension, and a pure theoretical paradigm skips empirical experiment review. Prompts require original evidence, counterevidence checks, source limitation reporting, no fixed issue count and resistance to instructions embedded in PDF text. No outside literature lookup occurs; such leads require `external_verification_required`.

P2-C will later consolidate candidates, and P3 will independently verify them. Neither occurs in this branch.

The three-paper real-model evaluation, public structured outputs, manual review notes, costs, and unresolved limitations are recorded in [the P2-B evaluation](p2b-real-evaluation.md). The separate ChatGPT web review comparison is pending because reference reviews have not yet been supplied.
