# P2-A: N1–N3 paper understanding

This branch starts from P1 squash merge `12a55b4d836084cbc2a07790596f6561043b6673`. The existing sampled review, candidate screening, countercheck, report, Evidence API, PDF reader and export paths are unchanged. The new API is backend only.

## Contracts and execution

`backend/p2a_schema.py` defines version `1.0` Pydantic contracts. All three results contain `document_id`, `source_bundle_id`, `review_run_id`, `prompt_version`, `schema_version`, `model_identifier`, `input_coverage`, and `execution_status`. N1 `ReviewPlan` holds paper type, domain, paradigm, applicable/priority/excluded review dimensions, and required/missing materials. N2 `PaperProfile` holds the research problem, motivation, author-claimed gap, method and components, assumptions, setup, datasets/metrics, results, contributions, conclusions, author-stated limitations, source gaps and canonical evidence references. N3 `ClaimEvidenceMap` holds `Contribution`, `Claim`, `SupportRelation`, `EvidenceGap`, and canonical `EvidenceReference` objects.

The engine uses P1 `reading_units[]` in order. A short input is read in one call. Longer input is split without omitting units. N2 asks the model for a concise global reconciliation of the four core narrative facts, then deterministically unions every part-level fact list and its source IDs. If that global call fails, all part-level lists are retained and a visible source gap states that core narrative synthesis fell back to the first part. N3 maps claims in smaller source parts with the complete profile available to the pipeline; each call receives the profile facts whose source IDs map to that part, plus author-claimed contributions. Deterministic consolidation assigns unique IDs and preserves relations without requesting another large response. `input_coverage` records which units entered the pipeline, not semantic completeness of the final answer. N1 sees a representative reading sample and the full section inventory for planning; the prompt explicitly forbids treating unsampled sections as absent. No output is a review finding. Model-supplied source IDs are resolved server-side against actual Source Bundle objects. Validation rejects missing IDs, foreign snapshots or documents, duplicate contribution/claim IDs, broken relations, uncited profile facts, and claims with neither a support relation nor an explicit evidence gap. A limited parser input produces `execution_status=limited`; it cannot be promoted to verified by the model.

Prompt templates: `paper-type-planner/v1`, `paper-understanding/v1`, `contribution-evidence-mapper/v1`. They contain no Shaw-specific answers. Formula, table and figure status is presented as unverified unless P1 has independent human reference; the profile must carry unresolved source gaps.

## API and storage

`POST /api/documents/{document_id}/understanding-runs` starts an isolated background run (optional `target_journal`, `special_requirements`). `GET /api/understanding-runs/{run_id}` returns status, completed stage results and call metadata. Each call trace is saved immediately; a completed N1 remains available if N2 fails. `GET /api/understanding-runs/{run_id}/source-bundle` retrieves the exact bundle snapshot used by that run. These routes use the existing `/api/*` session protection. The new SQLite tables are independent of `review_runs` and never feed the historical review algorithm. On startup, interrupted P2-A runs are marked failed. Existing SQLite files gain only the new tables; an early development version of the P2-A table gains `source_bundle_json` via additive migration. Existing usage summaries also include these calls under `understanding`.

The local `data/` directory and `.env.local` remain gitignored. The run table stores the Source Bundle snapshot and validated results in that local database. The call table stores prompt version, requested/returned model IDs, token counts, elapsed time, status and sanitized error class; it does not store API keys, full model input or raw response. Detailed real-test inputs and raw outputs are saved under a private, mode-0700 `data/p2a-evaluation/runs/` directory with mode-0600 files and are not uploaded to GitHub. The local evaluation runner redacts the configured API key before writing any request or response. Operators must set an access token and a retention policy before exposing this local service beyond the trusted machine; automatic production data expiry is not implemented in P2-A.

## Verification and limitations

Mock tests exercise all three contracts, full-unit coverage, long-input synthesis, reference and snapshot validation, retry/failure paths, secret-free error traces, API persistence and baseline isolation. Real-model quality must be evaluated separately. The [public Shaw 2018 PDF](https://arxiv.org/pdf/1803.02155) and a held-out [public DistilBERT 2019 PDF](https://arxiv.org/pdf/1910.01108) are used for local end-to-end runs; neither paper is embedded in prompts. The measured runs and human academic checks are in [p2a-real-evaluation.md](p2a-real-evaluation.md). Public Shaw output examples are in [examples/p2a-shaw2018](examples/p2a-shaw2018). These examples contain validated structured results, not actual model inputs or raw responses.

P1's geometric reading order, section boundaries and technical object transcription remain candidates. A `blocked` whole-paper scope stops before any model call; `needs_review` propagates as `limited`. N2/N3 cannot certify equation, table or figure correctness. A missing object in parser output is a source gap, not evidence that the authors omitted it. External literature validation, multi-dimensional issue generation, counterchecks, severity, and reports remain outside P2-A.

The public Shaw PDF produced 167 reading units. Whole-paper section readiness is `needs_review` due to ambiguous order, incomplete section assignment/source mapping, and absent human reading/page references. Table 1 has incomplete structure; Tables 2 and 3 are detected but unverified; equations (1)–(5) are transcription candidates; Figure 1 needs visual review. The model may use these as leads but must not present their structure or meaning as independently verified. Table 3's candidate rows are `Yes/Yes/25.8`, `No/Yes/25.8`, `Yes/No/25.3`, `No/No/12.5`; those row/column assignments are not promoted to verified evidence by P2-A.
