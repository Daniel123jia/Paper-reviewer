# P2-C candidate consolidation and coverage audit

P2-C starts from P2-B squash commit `a3b405e4905b1c558174e45f54a6fc0d0b58130a`. It organizes existing unverified candidates. It does not rerun six-dimensional review, verify scientific claims, or write findings into the legacy report workflow.

## Frozen input and contract

`backend/p2c_schema.py` defines independent schema version `1.0`: `OriginalCandidateInventory`, `CandidateRelation`, `ConsolidatedIssue`, `CandidateLineage`, `CoverageGap`, `CoverageAudit`, `VerificationTask`, and `CandidateConsolidationResult`. Every result binds the document ID, PDF snapshot ID/SHA-256 when available, Source Bundle ID, P2-A understanding run, P2-B professional review run and P2-C consolidation run. The inventory also records upstream schema and dimension Prompt versions.

`backend/p2c_normalizer.py` accepts only P2-B `completed` or `limited` results by default. It rejects partial/failed/budget-exceeded runs, mismatched IDs or snapshots, duplicate Issue IDs, unknown Claim IDs, and source objects absent from the frozen Source Bundle. Existing P2-A/P2-B Pydantic and source-reference validators are reused. The original `IssueCandidate` objects are copied into a complete, indexed inventory without modifying P2-B storage. Indexes cover dimension, claim, contribution and both positive/counterevidence source IDs. The API checks the database document snapshot against the P2-A frozen bundle before launch. A shortened public Evidence Mapping JSON is never accepted as a full Source Bundle.

## Semantic grouping and loss checks

`backend/p2c_grouping.py` evaluates **every candidate pair** in bounded batches, so a screening heuristic cannot silently omit a possible merge. The versioned `candidate-semantic-grouping/v1` Prompt classifies exact duplicates, semantic duplicates, related but distinct questions, distinct questions, and uncertain relations. It compares the questioned scientific object and verification evidence rather than titles alone. `candidate-group-reconciliation/v1` then proposes a complete partition across all candidates. For larger candidate sets, pair batches continue until all pairs are accounted for or the configured budget is exhausted; unavailable comparisons become explicit `uncertain_relation` records, and their candidates stay separate.

The server rejects invented or omitted pair/issue IDs and checks every proposed group's full pairwise relation graph. A transitive chain cannot force a three-way merge: a group is split into pairwise-compatible subgroups. The model supplies relation judgments and grouping rationale; the server generates stable issue IDs from the document, P2-B run and sorted member IDs. It assembles the issue's observed facts, scientific concerns, impact assessments, verification questions, evidence roles, counterevidence and limitations directly from the originals. External-verification flags are combined conservatively and disagreement is recorded. Conflicting impact assessments become `undetermined`, not a confirmed Major concern. `CandidateConsolidationResult` validates one-to-one lineage, full pair accounting and no evidence, claim, question, limitation or original concern loss. All consolidated issues remain `unverified`.

Invalid model JSON, omitted pairs, contradictory group proposals and model errors cause a recorded retry or conservative separation. The independent budget uses `P2C_MAX_CALLS` (default 16), `P2C_MAX_INPUT_TOKENS` (200000), `P2C_MAX_OUTPUT_TOKENS` (50000), and `P2C_MAX_DURATION_MS` (1800000). Unknown Token usage consumes a conservative reservation through the existing P2-A `RunBudget`; it is also counted separately. Traces store requested/actual model, Prompt version, known Tokens, duration, status and error **class**; they do not store a raw request, response or key in SQLite.

## Coverage and P3 handoff

`backend/p2c_coverage.py` records D1–D6 execution/applicability/coverage, P2-A contribution and Claim inspection reports, P2-B candidate links, configured professional focus, source limitations and unresolved gaps. Its evidence level is explicitly `model_report_only`. A dimension with no candidates but a valid inspection explanation remains reviewed; a missing, failed or source-blocked dimension becomes a gap even if its P2-B execution status says `limited`. Partial source coverage stays `reported_partial`; an unverified formula/table/figure or P2-A EvidenceGap produces a source-quality gap. Generic rules, required external material and missing ReviewPlan material are explicit limits. `CoverageGap` describes unfinished review or source access, never an author error.

`backend/p2c_engine.py` creates one `VerificationTask` for each consolidated issue. It carries the exact frozen snapshot, all original candidate IDs, positive/counterevidence refs, original questions, external-material needs, limitations and a provisional verification priority. P3 must independently check these tasks; no task is pre-verified.

## API, persistence and compatibility

Authenticated `POST /api/professional-review-runs/{run_id}/consolidation-runs` starts a P2-C run for a complete P2-B snapshot. An accidental repeated start returns 409; an explicit `{"retry": true}` body allows a new run after a terminal result while preserving earlier history. Concurrent active runs remain prohibited. Authenticated `GET /api/candidate-consolidation-runs/{run_id}` exposes the run state, original inventory, persisted relation batches, final result when available and safe call metadata. Separate SQLite tables retain the run, relation batches and model calls. A restart marks interrupted work `partial_failed` if its inventory or a batch was saved, otherwise `failed`. A model/budget limitation retains all originals and explicit uncertain relations.

No P2-A/P2-B schema, P2-B raw candidate, old review Prompt, old report export or frontend page is modified. The [real-paper evaluation](p2c-real-evaluation.md) contains the three-public-paper results and manual merge review. ChatGPT web deep-review parity remains pending until independent reference reviews are supplied.
